# 07 持久化、重启与故障恢复

本章应在首次复用数据目录前阅读。Websearch 的恢复依赖本地任务日志与远端索引快照的对应关系，不能只备份其中一个文件后假设所有状态自然一致。

## 1. 两个目录、两个状态主体

Rust 的 `--data` 保存抓取日志与应用身份。JVM 的 `--index-data` 保存真正的索引。在本机监督入口中，默认会协调使用相同数据根，但这只是两个服务的路径选择，不意味着远端部署时磁盘自动共享。

```text
Rust 数据根
  .crawl.lock          抓取目录锁
  crawl.journal        任务、完成和检查点恢复依据
  dedupe.tsv           兼容性去重投影，不是恢复权威
  remote.identity      持久化应用身份与关联信息
  remote.components    精确远端部署意图

JVM 数据根
  .search.lock         搜索目录锁
  index/
    seg-....segment    完整索引代际快照
```

具体文件是否已出现取决于当前阶段。锁文件存在不等于进程仍活着；但不要在活进程持锁时删除锁文件绕过保护。先确认所有权和实际进程状态。

`--index-data /srv/search-A` 指 **JVM 所在机器**的绝对路径，不是把 Rust 本机文件传到那里。该选择会被持久化，后续 keep/serve-only 要遵守绑定关系。

## 2. 三种启动语义

普通抓取：没有 `--keep` 和 `--serve-only` 时，开始新索引。程序执行有序冷重置，而不只是“在原索引上继续添加”。

`--keep`：保留索引和已发现集合，校验检查点归属，恢复未完成任务并接受新任务。它不是强制重抓所有旧 URL。

`--serve-only`：隐含保留语义，只提供已有索引查询，不抓取且拒绝 seed。独立启动器只启动 JVM 角色；manifest 也按服务模式裁剪必要角色。

如果你只是想查看旧库，请使用 serve-only。用默认抓取命令启动后再发现数据清空，不是一个无副作用的“试启动”。

## 3. 冷重置为什么也需要日志

冷重置采用持久化 reset intent、JVM Clear 创建新 epoch、本地 Begin 等阶段。因为重置中也可能崩溃，程序必须知道“正在开始一个新库”，不能把旧任务与新空库错误拼接。

Clear 不是仅清除一个内存 HashMap；其持久化结果必须使整个 JVM 重启后仍然是新状态。测试只检查当前进程的空结果不够。

## 4. 检查点由什么组成

当前版本化检查点含 16 字节 epoch、u64 generation 与 32 字节摘要，回复总长为 56 字节。epoch 标识一条冷启动谱系，generation 标识同一谱系内的快照代际，摘要绑定具体内容。

同 epoch 且 generation 较大只是时间关系，还不足以证明新快照继承了旧检查点。JVM 要校验 ancestry 中的摘要关系，防止被同代际的另一份分叉索引冒充。

这也是为什么不能手工编辑 generation 让程序“继续”。错误应通过恢复正确的数据对或明确冷启动处理，而不是绕过校验。

## 5. 完成记录的关键顺序

```text
持久化发现意图
  -> frontier 调度与抓取
  -> 分词并验证
  -> JVM 完整文档替换
  -> DocumentsAck
  -> JVM CheckpointV2 并确认同步
  -> 本地 Complete 记录并同步
```

DocumentsAck 之前失败：不宣称该批文档成功。DocumentsAck 之后、检查点之前失败：内存可能已有文档，但持久化未知。检查点之后、本地 Complete 之前失败：远端已有文档，本地可能重放。Complete 确认后：恢复可依据这条匹配检查点的完成记录。

重放同一完整文档替换原词集合，因此不会累积 TF。副作用发生次数仍可能大于一次，这属于业务幂等下的至少一次提交，而不是所有网络消息恰好一次。

## 6. JVM 快照如何保存

当前快照是完整索引，不是任意多小段的增量合并数据库。写入使用临时文件、文件同步、原子发布和目录同步等步骤；确认失败会被视为效果可能不确定，组件采取保守失败策略，不能继续返回“已持久化”。

最新格式为 v5，保存当前 epoch 的代际与历史摘要。旧格式 v1 到 v4 可读取并迁移；旧程序不一定能读取新 v5。升级前应保留可恢复备份，不能认为二进制回滚天然兼容新数据。

最新快照损坏时应明确失败，不能默默选一个旧文件继续服务。否则用户看到“启动成功”，实际却悄悄丢失最近提交。

背景清理可保留最新完整快照并压缩历史存储，但必须先完成必要历史验证。历史摘要条目也有上限，不代表可以无限运行而无需关注容量。

## 7. 准备索引与服务模式

恢复前的 `PrepareIndex` 支持检查旧历史。当前协调逻辑有轮询和总超时，不是一个无限阻塞的初始化调用。服务模式不应为了查询而不必要地重写索引准备状态，冷 Clear 则有独立路径。

初始化耗时长时，先检查快照数量、磁盘 I/O 和历史校验日志；不要直接扩大所有超时掩盖损坏或无法访问的目录。

## 8. 本地 journal 与压缩

当前日志格式标识为 `PRWSJ2\n`，记录通过前向摘要关联，支持任务快照分块与 Seal。恢复必须检查完整性和结构，不应忽略中间坏记录继续猜测状态。

日志有约 256 MiB 总预算、2 MiB 单记录预算和 100,000 任务预算。达到一定冗余历史后可以压缩为新的任务快照，先写 `.crawl.journal.next`，再同步和发布。

压缩的目的不是忘掉去重集合，而是在保留必要发现与完成状态的前提下去掉重复历史。只保存 pending、丢掉已发现集合，会使重启后反复抓同一站点。

旧日志迁移有兼容路径；没有摘要的历史不能凭空获得已有内容证明，需要按实现采用保守重放。`dedupe.tsv` 仅为投影，不应单独拿它替代 journal。

## 9. 主要容量边界

JVM 快照当前有约 256 MiB 文件、1,000,000 文档、1,000,000 词项、16,000,000 postings 和 16 MiB 字符串等硬上限；历史代际/摘要数量也有限。精确校验见 SnapshotStore。

这些是拒绝异常输入或资源耗尽的边界，不是推荐生产容量。完整快照发布需要额外磁盘空间，Actor 内存索引需要额外堆内存，Python/Ray 与 JVM 各自还有运行时开销。

容量估算要观测实际语料：平均文本长度、不同词项数、posting 数、快照大小、提交延迟和峰值内存。不能只用 `--pages` 推导堆容量。

## 10. 正确备份与恢复步骤

1. 正常停止抓取和服务，确认最后持久化及退出结果。
2. 确认 Rust 和 JVM 都不再写对应数据根。
3. 成套备份 journal、identity、component intent 与 JVM 索引；记录两个目录的关联、程序版本和制品摘要。
4. 将备份恢复到独立位置，使用匹配配置启动 serve-only。
5. 比较文档数、URL 集合、查询结果和分数，检查无新的网页抓取请求。
6. 确认恢复可用后再考虑以 keep 恢复工作。

活跃写入时直接递归复制两个目录不是一致性备份协议。跨机路径变化还可能触及持久化的 index-data 绑定，需要按程序规则规划迁移，而不是随手改 identity。

## 11. 常见失败的正确反应

目录锁冲突：找出占有进程，确认是否启动重复实例。不要删锁强行并发。

epoch、generation 或摘要不匹配：保留原目录，检查是否把 journal 配错索引、是否回滚了部分备份或复用了别的应用目录。不要修改摘要让检查通过。

最新快照损坏：复制保存故障证据，从已验证的一致备份恢复；若允许丢弃旧库，应明确选择新目录冷启动。不能宣称“自动回退后无损恢复”。

同步或磁盘写入失败：确认剩余空间、目录权限和文件系统状态。上次操作可能生效也可能没完全持久化，不要凭一次异常就断言什么都没有写。

## 12. 如何证明恢复正确

至少比较崩溃前后的精确 URL 集合与分数，验证重复提交不增加 TF，更新删除旧词、零词更新清掉旧 postings，检查 journal 不会提前完成任务。

还要在远端检查点之后、本地完成之前注入故障，重启整个 JVM，而不只是重建 Rust 对象。进程 SIGKILL 测试与真正断电文件系统测试是不同证据，不能互相替代。
